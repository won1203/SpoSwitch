# 스포스위치 (SpoSwitch) 설계 문서 v2.0

> 개정일: 2026-09-13  
> 문서 성격: 구현 기준안과 단계별 작업 명세  
> 대응 요구사항: [PRD v3.2](스포스위치_PRD_v3.2.md)  
> 현재 상태: 기능별 패키지로 분리된 Android UI 목업. 실제 API·백엔드·DB 연결 전.

## 1. 설계 기준

기존 설계 문서, PRD v3.1, 최신 사용자 흐름, 이후 구현 계획을 통합한다. 충돌 시 최신 사용자 요구사항을 우선한다. 원본 문서의 코드 생성 지시, 실행 예시, 과거 검증 기록은 현재 실행 지시나 현재 환경의 검증 결과로 취급하지 않는다.

이 문서는 구현을 위한 계약안이다. 아래 ‘제안’ 구조와 정책은 각 단계에서 검증·확정하며, 문서에 등장하는 API·테이블이 이미 구현되어 있다는 의미가 아니다. 이번 개정에서는 애플리케이션 코드, 서버, DB를 변경하지 않는다.

| 항목 | 최신 기준 |
|---|---|
| 첫 진입 | 홈에서 위치·날씨 먼저 표시; 프로필 입력과 분리 |
| 사용자 입력 | 성별·연령대 → 키·몸무게 → 운동 목표 |
| 개인화 | 국민체력100 콘텐츠를 검증된 조건으로 매칭 |
| 시설 | 공공·민간을 포함하고 위치·현재 환경·운동 적합성을 반영한 서울 내 반경 3km 조회 |
| 날씨 정책 | 정상 시 실내·실외 균형 추천, 비·눈·미세먼지 악화 시 실내 우선 |
| 사용자 데이터 | MVP는 로그인 없이 프로필·최근 위치·설정을 기기에 저장 |
| 자동화 | 공통 추천 정책을 이용한 환경 전환 및 선택적 알림 |
| 기술 도입 | 현재 네이티브 View UI를 유지하며 기능별 상태와 데이터 접근 분리 |
| 개발 순서 | 데이터 검증·계약 → 기반 → 위치·날씨 → 프로필 → 운동 → 시설 → 알림 |

## 2. 현재 구조와 변경 목표

### 2.1 현재 확인한 UI 구조

| 위치 | 현재 역할 |
|---|---|
| `MainActivity.kt` | 앱 진입, 화면 전환, 상태 복원 연결 |
| `app/AppRoute.kt`, `app/AppState.kt`, `app/FeatureUiScope.kt` | 경로, 공용 목업 상태, 화면 구성 접근점 |
| `feature/home` | 홈 |
| `feature/profile` | 상태 입력·프로필 |
| `feature/prescription` | 운동 처방 화면 |
| `feature/facility` | 시설 목록·상세·날씨 전환 안내 |
| `feature/weather` | 날씨 상세 |
| `data/mock` | 목업 콘텐츠 |
| `model` | 목업 시설·날씨 모델 |
| `ui/component`, `ui/theme` | 공통 UI와 디자인 |

패키지 분리는 완료되었지만 화면이 공유 가변 상태와 목업 데이터를 직접 사용하는 부분이 있다. 현재 상태 복원과 실제 프로필 영속 저장은 구분해야 한다. UI 목업의 영상 상태·거리·이미지·날씨는 실데이터 연동 결과가 아니다.

### 2.2 목표 구조 — 제안

```text
Android 화면 → 기능별 ViewModel / UiState → Repository 인터페이스
                                         ├─ Mock 구현
                                         ├─ 로컬 저장 구현(프로필·최근 위치·설정)
                                         └─ 데이터 API 구현(날씨·운동·시설)
                                                    ↓
                                           Spring Boot API 서버
                                         ├─ 공공 데이터 조회·정규화
                                         ├─ 운동·시설 데이터 제공
                                         └─ MySQL / 지역별 환경 캐시
```

- `MainActivity`는 화면 구성·탐색·권한 결과 전달에 집중한다.
- 화면 상태는 Home, Profile, Prescription, Facility, Weather 단위로 소유한다. 화면을 넘는 원본 데이터는 Repository에서 공유한다.
- 화면에 필요한 값은 불변 `UiState`로 전달하고 사용자 동작은 이벤트로 받는다.
- 네트워크 응답 DTO, 앱 데이터 모델, 표시 모델을 필요에 따라 분리한다. 시설 거리의 원본은 숫자(m), 리소스 ID와 거리 문구는 UI에서 관리한다.
- 저장한 프로필과 입력 중 초안을 구분한다. 로컬 저장 실패를 저장 성공처럼 표시하지 않는다.
- 프로필은 로컬 Repository에, 환경·운동·시설은 데이터 Repository에 둔다. 이 경계를 이용해 목업을 순차 교체한다. 초기부터 다중 Gradle 모듈이나 UI 프레임워크 전환을 요구하지 않는다.
- 위치 권한 상태와 서버의 지역명 변환 실패를 별도로 처리한다.

### 2.3 서버 구조와 빌드

서버는 기능별 패키지로 나눈 단일 애플리케이션을 기준안으로 한다.

| 서버 기능 | 책임 |
|---|---|
| `environment` | 좌표 변환, 지역명, 관측·예보·대기 조회·캐시·품질 판단 |
| `prescription` | 운동 콘텐츠 적재·조회·조건 매칭 |
| `facility` | 시설 적재·분류·반경 조회 |
| `recommendation-policy` | 앱과 공유할 환경 판단 기준·정책 버전 관리 |
| `notification` | FCM 선택 시 계정 없는 기기 등록, 상태 전환, 발송 이력·재시도 |

Java 21, Spring Boot 4.1.1, MySQL 8 계열을 기존 계획의 기준안으로 유지한다. 정확한 DB 배포 버전은 M3에서 고정한다. 현재 Android Gradle Wrapper는 8.11.1이므로 서버 빌드와 분리한다. 계획 검토 시 확인한 Spring Boot 4.1.1 요구사항은 Gradle 8.14 이상 또는 9 계열이며, 서버 생성 시 사용할 버전의 공식 요구사항을 다시 확인한다.

MVP 서버는 사용자 계정·프로필을 저장하지 않는다. 개인화 조건과 최근 위치는 Android 기기에 보관하고 추천 조합은 기기에서 수행한다. 공공 API 키 보호, 데이터 캐시와 배치 적재를 위한 서버는 사용자 계정과 분리해 운영한다. 추후 로그인 도입이 확정되면 계정·동기화 기능을 별도 설계한다.

## 3. 사용자 흐름과 상태 전이

```text
실행 → 홈 즉시 구성 → 위치 권한/수동 지역 → 환경 조회
                         ↓
           프로필 없음: 입력 CTA / 프로필 있음: 추천 조회
                         ↓
      성별·연령대 → 키·몸무게 → 목표 → 저장 → 운동 추천
                         ↓
                운동 상세·영상 / 시설 탐색
                         ↓
                 시설 상세 → 외부 길안내
```

환경 조회는 프로필과 FCM 등록에 의존하지 않는다. MVP에는 로그인 세션이 없으며 환경·프로필·시설 영역은 각자 로딩·오류 상태를 가진다.

| 상태 | 표시·동작 |
|---|---|
| 위치 미결정 | 위치 사용 안내와 수동 지역 선택 |
| 위치 취득 중 | 위치 영역의 진행 상태; 다른 홈 요소 유지 |
| 수동 선택 | ‘선택한 지역’ 표시, 해당 지역 대표 좌표 사용 사실 안내 |
| 행정동 변환 실패 | 확인 가능한 시·구까지 표시; 예시 행정동 생성 금지 |
| 환경 일부 누락 | 확인한 값과 누락·기준 시각을 함께 표시 |
| 프로필 미완료 | 개인화 추천 대신 상태 입력 CTA |
| 추천 없음 | 조건 변경 또는 검증된 공통 콘텐츠 안내 |
| 서울 밖 | 서비스 범위 안내와 서울 지역 선택 |

알림 클릭은 저장된 문구만 보여주는 대신 현재 환경과 추천을 다시 조회한다. 앱 종료 상태에서 진입할 때에도 로컬 프로필을 복원한 후 해당 화면으로 이동한다.

## 5. 환경 모델과 판단 규칙

### 5.1 데이터 계약

`EnvironmentSnapshot`은 위치, 관측, 예보, 대기, 판단 결과를 구분한다.

| 영역 | 핵심 필드 |
|---|---|
| 위치 | `latitude`, `longitude`, `locationSource`, `locatedAt`, `accuracyMeters`, `regionCode`, `displayAddress` |
| 관측 | `temperatureC`, `precipitationType`, `observedAt`, `fetchedAt`, `quality` |
| 예보 | `issuedAt`, `validAt`, 강수·하늘·기온, `quality` |
| 대기 | `stationId`, PM10/PM2.5 농도·등급, `observedAt`, `fetchedAt`, `quality` |
| 판단 | `mode`, `reasons`, `evaluatedAt`, `policyVersion` |

필드명은 제안이다. 품질은 `FRESH`, `STALE`, `MISSING`, `ERROR` 등으로 구성하고 추천 모드 `INDOOR_PRIORITY`, `BALANCED`, `UNKNOWN`과 분리한다. 과거 관측값을 재조회했다고 최신 관측으로 바꾸지 않는다. 시각은 UTC 또는 오프셋을 포함한 ISO 8601로 전달하고, 발표·대상 시각 계산과 한국 사용자 표시는 KST 기준으로 처리한다.

### 5.2 판단 알고리즘

1. 관측·대기 각각의 필수 필드와 유효 기간을 검사한다.
2. 유효한 현재 비·눈 또는 확정한 전환 기준 이상의 미세먼지가 있으면 `INDOOR_PRIORITY`로 판단하고 확인한 사유를 모두 반환한다.
3. 필수 자료가 모두 유효하며 실외 활동 방해 조건이 없으면 `BALANCED`로 판단해 실내·실외 시설을 같은 비중으로 추천한다.
4. 악화가 확인되지 않았어도 필수 자료가 누락되거나 오래되었으면 `UNKNOWN`으로 반환한다.
5. 예보의 강수 예상은 별도 안내로 제공한다. 현재 비가 오는 것으로 치환하지 않는다.

초단기실황과 단기예보의 강수 코드를 동일한 숫자 의미로 취급하지 않고 원천 어댑터에서 정규화한다. 기상 격자 변환은 좌표 샘플로 검증한다. 예보는 날짜와 시간을 결합해 선택하여 자정 경계를 처리한다. 최신 발표 자료가 아직 제공되지 않으면 이전 발표로 대체하되 실제 발표 시각과 품질을 유지한다.

관측·대기·예보·위치의 TTL, 재시도 간격, 캐시 만료 정책은 D-06에서 수치로 확정한다. 서버가 이용할 수 없는 자료를 앱에서 임의로 정상 처리하지 않는다.

미세먼지·초미세먼지의 정확한 전환 등급과 둘 중 하나만 악화될 때의 처리 기준은 M2에서 실제 원천 등급과 공공 기준을 확인해 확정한다. `INDOOR_PRIORITY`는 실내 시설을 상단과 주요 추천 영역에 먼저 배치한다는 뜻이며, 실외 시설을 반드시 전부 숨긴다는 뜻은 아니다.

## 6. 프로필·운동 매칭 설계

프로필은 `gender`, `ageGroup`, `heightCm`, `weightKg`, `goalCode`를 가진다. 성별 선택 안 함을 지원하고 키·몸무게는 단위가 명확한 숫자로 저장한다. 수집 목적과 추천에 실제 사용하는 항목을 UI에 안내한다.

| 목표 코드 | 체력요인 후보 |
|---|---|
| `STRENGTH_MUSCLE` | 근력, 근지구력 |
| `FAT_LOSS` | 심폐지구력, 근지구력 |
| `FLEXIBILITY_POSTURE` | 유연성, 평형성 |
| `GENERAL_FITNESS` | 심폐지구력, 근력 |

매핑은 원천 고유 값을 확인한 뒤 확정한다. 입력 검증 범위도 MVP 대상 연령과 함께 확정하며 목업의 수치를 의학적 기준으로 취급하지 않는다.

추천 처리 순서는 다음과 같다.

1. 프로필 완료와 목표 코드를 확인한다.
2. 원천 연령 대상·명시적 제한을 검사한다. 원천의 ‘공통’은 확인된 의미에 따라 사용한다.
3. 목표를 체력요인 후보에 연결하고 운동 장소·지원 조건을 적용한다.
4. 중복 콘텐츠를 정리하되 해당 콘텐츠의 복수 연령·목표·태그 연결은 유지한다.
5. 추천 이유, 원천 식별자, 영상·썸네일·출처 정보를 반환한다.

결과가 없으면 명시적 제한을 해제하지 않는다. 검증된 공통 콘텐츠만 대안으로 제공하거나 결과 없음을 반환한다. 신체 정보만으로 체력 수준·강도·세트 수를 산출하지 않는다. 목업의 시간·횟수·영상 길이를 실데이터처럼 채우지 않는다.

기존 `file_nm` 한 필드의 유일 제약만으로 전체 운동 레코드를 덮어쓰지 않는다. 원천별 콘텐츠 식별 범위를 먼저 확인하고 영상 본체, 제공 파일, 분류 연결을 분리해 필요한 관계를 보존한다. 재생 URL 실패 시 검증한 원문 또는 외부 링크를 제공한다.

## 7. 시설 수집과 공간 조회

- 시설 원천 ID를 기준으로 멱등 갱신하고 이름·주소·좌표·운영 상태·종목·운영 주체를 보존한다.
- 정상 운영 여부와 좌표 유효성을 확인한다. 기존의 대략적 서울 경계 상자는 이상값 검사용이며 서울 행정구역 판정의 최종 근거로 쓰지 않는다.
- 실내외 분류는 명시값을 우선하고, 종목 기반 추론에는 `classificationSource`와 규칙 버전을 남긴다. 수영장·골프장 등 예외와 미분류를 처리한다.
- 실내라는 이유만으로 근력 운동 사용자에게 당구장 등을 추천하지 않는다. 시설의 종목과 운동 목적 적합성을 추가 확인한다.
- 공공시설과 민간시설을 모두 조회 대상으로 삼는다. 운영 주체를 확인할 수 있으면 표시하고, 확인되지 않은 시설을 임의로 공공 또는 민간으로 표시하지 않는다.

조회는 사용자 또는 수동 지역 기준점에서 3,000m 이내를 정확 거리로 필터링하고 거리순, 동일 거리에서는 안정적인 ID순으로 정렬한다. 원본 거리는 m 단위 숫자로 반환한다. 페이지가 달라도 동일 조건의 정렬과 중복 방지 규칙을 유지한다. 결과가 없으면 자동으로 반경을 늘리지 않는다.

공간 컬럼은 MySQL의 지리 좌표계 SRID 4326을 기준안으로 한다. API에서는 `latitude`와 `longitude` 이름으로 좌표 의미를 명확히 하고 DB 입출력은 축 순서를 명시한다. `POINT(lng, lat)` 문자열만으로 항상 원하는 축 순서가 보장된다고 가정하지 않는다. 실제 MySQL 버전에서 거리·경계·축 순서 테스트를 수행한다.

공간 인덱스가 거리 함수만으로 활용된다고 단정하지 않는다. 필요하면 후보 범위를 먼저 좁히고 정확 거리 필터를 적용한다. 실제 데이터에서 실행 계획을 확인한다. 과거 MariaDB 검증 기록은 MySQL 검증을 대체하지 않는다.

## 8. 논리 데이터 모델 — 제안

실행 DDL은 M3에서 원천 스키마와 DB 버전을 확정한 뒤 마이그레이션으로 작성한다.

| 저장 위치·엔터티 | 주요 속성 | 관계·제약 |
|---|---|---|
| Android `local_profile` | 성별, 연령대, 키, 몸무게, 목표, 수정 시각 | 앱 전용 저장소, 서버 전송·계정 연결 없음 |
| Android `local_location` | 좌표, 지역 코드·표시명, 출처, 정밀도, 취득 시각 | 최신 위치와 수동 선택 구분, 로컬 보관 |
| Android `local_settings` | 알림 동의, 필터, 마지막 추천 모드·정책 버전 | 앱 재실행 시 복원 |
| 서버 `facility` | 원천 ID, 이름, 주소, 좌표, 종목, 실내외, 운영 상태·주체 | 공공·민간 포함, 원천 ID 유일, 공간 인덱스 검토 |
| 서버 `exercise_content` | 내부 ID, 원천·콘텐츠 키, 제목, 안내, 출처, 갱신 시각 | 검증한 원천 식별 범위 내 유일 |
| 서버 `exercise_media` | 콘텐츠 ID, 영상·썸네일 URL, 원천 파일 키 | 콘텐츠 FK, 복수 파일 보존 |
| 서버 `exercise_attribute` | 콘텐츠 ID, 분류 종류, 원천 값 | 콘텐츠 FK, 복수 연령·목표·요인 연결 |
| 서버 `goal_factor_mapping` | 목표 코드, 체력요인, 규칙 버전 | 확정한 매핑만 사용 |
| 서버 `environment_cache` | 지역·격자·측정소 키, 데이터, 자료·조회 시각, 품질 | 저장 방식은 DB/캐시 중 규모에 맞춰 결정 |
| 서버 `push_registration` | 익명 기기 등록 ID, 토큰, 지역 키, 동의, 갱신·무효 시각 | FCM 선택 시에만 사용, 프로필·계정과 연결 금지 |
| 서버 `notification_event` | 익명 기기 등록 ID, 전환 ID, 상태, 재시도, 발송 시각 | FCM 선택 시 전환별 중복 방지 |
| 서버 `ingestion_run` | 원천, 시작·종료, 성공·실패 건수, 상태 | 적재 운영 이력, 민감 응답 저장 금지 |

MVP 서버에는 `app_user`, `session_credential`, `user_profile`, `user_location` 테이블을 만들지 않는다. 사용자와 시설·운동 콘텐츠 사이의 추천 관계도 저장하지 않는다. 추천은 로컬 프로필과 공개 콘텐츠에 정책을 적용한 결과다. 추후 로그인·동기화를 도입할 때 사용자 데이터 모델과 마이그레이션·동의 절차를 새로 설계한다.

수집은 페이지 단위 검증·갱신을 수행하고 실패 페이지를 재처리할 수 있게 한다. 전체 수집 실패 시 정상 데이터를 비우지 않는다. 삭제·폐업·미노출 처리는 완전한 수집이 확인된 경우에만 확정 정책으로 반영한다.

## 9. API 계약 — 제안

### 9.1 공통 규칙

- JSON 필드·단위·nullable·코드 목록은 OpenAPI 계약으로 확정한다.
- MVP 데이터 API는 사용자 계정과 `/me` API를 제공하지 않는다. 프로필·최근 위치·설정은 Android 로컬 저장소가 소유한다.
- 환경·시설 조회에 전달한 좌표와 필터는 응답 생성에만 사용하고 사용자 계정이나 프로필로 저장하지 않는다.
- FCM을 선택하면 익명 기기 등록과 해제 계약을 별도로 둔다. FCM 토큰은 로그인 자격이나 사용자 계정이 아니다.
- 공공 API 인증키는 서버에서 관리한다. 지도 SDK 등 앱에 필요한 키는 공급자가 지원하는 앱·서명 제한을 적용한다.
- 실패는 `error.code`, `error.message`, `error.retryable`, `requestId` 형태를 기준안으로 한다. 빈 검색 결과는 정상 빈 목록으로 구분한다.
- 위치가 요청·서버 진단에 포함될 수 있으므로 접근 로그와 오류 추적에서 좌표·자격·신체 정보를 마스킹한다.

### 9.2 엔드포인트

| 메서드·경로 | 입력·역할 | 주요 응답·조건 |
|---|---|---|
| `GET /api/v1/environment` | 좌표 또는 검증된 수동 지역 코드 | 환경 스냅샷; 프로필·FCM 없이 이용 |
| `GET /api/v1/prescriptions` | 연령·목표·체력요인 등 공개 필터 | 원천 태그·출처를 포함한 운동 목록 |
| `GET /api/v1/prescriptions/{id}` | 콘텐츠 ID | 운동 안내·원천 태그·영상·출처 |
| `GET /api/v1/facilities` | 좌표·실내외·종목·페이지 | 거리 포함 목록·다음 페이지 정보 |
| `GET /api/v1/facilities/{id}` | 시설 ID | 검증된 상세 정보·좌표 |
| `POST /api/v1/push/registrations` | FCM 선택 시 토큰·지역 키·동의 | 익명 등록 ID와 갱신 정보; 프로필 전송 없음 |
| `DELETE /api/v1/push/registrations/{id}` | FCM 수신 해제 | 등록·토큰 무효화 |

환경·운동·시설 API에는 사용자 로그인이 필요하지 않다. 인증 없는 API의 호출량 제한과 앱 식별 방식은 M3에서 정한다. FCM 등록 API는 M9에서 실제 알림 방식을 선택할 때 확정하며, 로그인·프로필 API는 후속 로그인 기능이 결정되기 전에는 범위에 포함하지 않는다.

로컬 프로필 저장 모델 예시는 다음과 같다. 연령 코드는 원천 값과 제품 입력 범위를 확인한 뒤 확정한다.

```json
{
  "gender": "UNSPECIFIED",
  "ageGroup": "TWENTIES",
  "heightCm": 170.0,
  "weightKg": 65.0,
  "goalCode": "STRENGTH_MUSCLE"
}
```

앱의 추천 결과는 추천 이유와 자료 품질을 분리한다. 예: `mode=INDOOR_PRIORITY`, `reasons=[PRECIPITATION]`, `airQuality=MISSING`이면 현재 강수에 근거해 실내를 우선하면서 대기 자료 누락도 알린다. 이 예시는 실제 API 응답이 아니다.

## 10. 환경 감시와 FCM

1. FCM을 선택한 경우 알림 동의·유효 토큰·유효 지역 키를 가진 익명 기기 등록을 지역별로 묶는다. 프로필과 정밀 위치는 전송하지 않는다.
2. 격자·측정소별로 환경을 공유 조회한다. 기기별 공공 API 호출을 반복하지 않는다.
3. 앱 추천과 동일한 서비스·정책 버전으로 모드를 평가한다.
4. 처음 얻은 유효 판단은 기준 상태로 저장하고 알림을 발송하지 않는다.
5. 유효한 `BALANCED → INDOOR_PRIORITY` 전환에 알림 이벤트를 저장한다. `UNKNOWN`을 정상 상태로 간주하지 않는다.
6. 이벤트를 비동기 발송하고 결과·재시도를 기록한다. 상태 갱신과 이벤트 생성은 원자적으로 처리한다.
7. 앱은 알림 이벤트 ID로 중복 표시를 억제하고 클릭 시 최신 추천을 조회한다.

서버 재시작·중복 스케줄 실행·발송 재시도에 대비해 전환 식별자와 유일 제약 또는 동등한 내구성 있는 중복 방지 구조를 사용한다. 외부 발송과 응답 저장 사이의 실패로 재전송될 수 있으므로 서버 기록만으로 정확히 한 번 전달을 보장한다고 표현하지 않는다.

`UNKNOWN` 구간을 거친 복귀, 정책 버전 변경, 조용한 시간 중 발생한 전환의 처리 규칙은 D-08에서 정한다. 좋은 날씨로 회복될 때의 별도 알림은 아직 확정하지 않는다. 오래된 지역 정보로 알림을 계속 보내지 않으며, MVP는 최근 포그라운드 위치 또는 수동 선택 지역을 로컬에서 관리한다. 상시 위치 추적은 후속 범위다.

| 단계 | 구체 작업 | 선행 | 종료 조건 |

| M2 데이터 검증 | 원천 API·코드·영상·주소·측정소 검증 | M1 | 필드표·샘플·제약·대체 경로 확보 |
| M3 계약 설계 | OpenAPI, 로컬 저장, 서버 DB, 무로그인 호출 정책, TTL, 오류 규격 | M2 | 화면과 서버가 공유할 계약 확정 |
| M4 기반 | 기능별 ViewModel·Repository, 독립 서버 빌드, DB 마이그레이션 | M3 | 목업/실연동 전환 가능한 실행 기반 |
| M5 위치·환경 | 권한·수동 지역, 주소·기상·대기 어댑터, 홈 연결 | M4 | 프로필 없이 실제 환경·실패 상태 표시 |
| M6 프로필 | 입력 검증, 로컬 저장·조회·수정, 재실행 복원 | M5 | 저장 성공·실패와 복원이 일치 |
| M7 운동 | 수집·분류·매칭, 추천 근거, 영상 재생 | M6 | 실제 운동 조회·재생·빈 결과 처리 |
| M8 시설 | 수집·분류·공간 조회, 지도·상세·길안내 | M7 | 3km·적합성·목록/지도 일치 검증 |
| M9 자동화 | 지역 감시·전환·이벤트·FCM·딥링크 | M8 | 중복·재시작·권한 거부 경로 통과 |
| M10 배포 | 통합 검증, 호출량·보안·삭제·운영·배포 설정 | M9 | PRD 출시 체크리스트 충족 |

각 단계에서 서버 기능과 해당 Android 연결을 함께 끝낸다. 첫 구현 목표는 M1~M6의 실제 환경 표시와 프로필 저장이다. 이후 M7~M8에서 핵심 추천 흐름, M9에서 자동 알림을 완성한다. 기간은 작업 인원·투입 시간과 API 승인 상태를 확인한 뒤 산정한다.

결정 항목 D-01~D-09와 확정 시점은 [PRD의 결정·검증 목록](스포스위치_PRD_v3.2.md#9-결정검증-목록)을 따른다. 미결정 항목을 임의의 확정 요구로 취급하지 않는다.

## 12. 검증 계획과 운영 준비

| 범위 | 필수 시나리오 |
|---|---|
| 환경 정책 | 정상, 비·눈, PM 악화, 복합 악화, 일부 누락, 오래된 값, 점검값 |
| 시각·좌표 | 자정 경계, 발표 지연, 날짜+시간 선택, 격자 변환, MySQL 축 순서 |
| 공간 조회 | 3km 안·밖·경계, 같은 거리 정렬, 서울 외, 잘못된 좌표, 실행 계획 |
| 운동 | 공통/제한 연령, 목표 매핑, 중복 파일의 복수 태그, 결과 없음, URL 실패 |
| 로컬 저장 | 프로필 수정·실패·재실행 복원, 앱 데이터 삭제, 서버 미전송 확인 |
| 수집 | 재실행 멱등성, 일부 페이지 실패, 원천 필드 변경, 정상 데이터 보존 |
| 알림 | 최초 무발송, 전환 1건 생성, 반복 감시, 재시작, 토큰 갱신, 수신 해제 |
| Android | 최초 실행, 권한 거부, 대략적 위치, 오프라인, 화면 재생성, 앱 종료 알림 진입 |

검증은 정책 단위 테스트, 원천 응답 계약 테스트, 실제 MySQL 통합 테스트, Android 주요 흐름 테스트로 나눈다. 실제 영상·위치·알림은 실기기에서도 확인한다. 기존 UI 목업 실행 확인이 실데이터 흐름 검증을 대체하지 않는다.

배포 전 운영 체크리스트:

- [ ] 공공 API별 호출 한도와 캐시·배치 주기를 계산했다.
- [ ] 수집 실패·조회 오류·발송 실패를 확인할 최소 운영 지표가 있다.
- [ ] 개발/운영 자격과 설정을 분리하고 실제 키를 저장소에 포함하지 않는다.
- [ ] 로그·오류 추적에 사용자 위치·신체 정보·인증 자격이 노출되지 않는다.
- [ ] 보관 기간·삭제 절차·백업·복구·DB 마이그레이션 절차를 확정했다.
- [ ] 목업 이미지·수치·영상 정보가 실데이터처럼 노출되지 않는다.
- [ ] 프로필 미완료·알림 거부 상태에서도 홈의 환경 조회가 동작한다.
- [ ] 원천 자료의 출처·기준 시각·누락 상태가 표시된다.

구현 중 임의의 진단 로그 파일을 저장소에 누적하지 않는다. 필요한 운영 진단은 설정된 보관·마스킹 정책에 따르고, 재사용할 검증 결과만 명시적인 문서로 남긴다.
